# 项目架构说明

项目名称：小童AI Agent智能学习助手（FastAPI + RAG 知识库 + Agent 服务化）

> 文档基线：2026-09-22。远端 `main` 已包含 9 月 20 日前的 Agent-RAG 融合、目标/任务工具、前端学习管家、超时重试和隔离测试。当前工作区继续完成 9 月 20 日统一配置、环境模板、四条冒烟测试和验收文档；正式测试为 37 条且全部通过。

## 一、项目简介

这是一个基于 FastAPI 的个人学习助手项目，目前包含四层能力：

1. 用户侧基础管理：注册/登录（JWT 鉴权）、学习目标、任务、文档管理，并按 `user_id` 隔离个人数据。
2. RAG 知识库问答：上传 PDF/DOCX 后解析、分块、向量化入库；提问时召回文档片段并交给 DeepSeek 回答，支持普通问答与 SSE 流式问答。
3. Agent 智能学习服务（已服务化）：利用 DeepSeek Function Calling 让大模型自动调用目标、任务和知识库工具，通过 Redis 保存多轮会话上下文，并提供会话列表、历史查询和会话删除接口。正式服务可创建目标、创建任务、查询目标和任务、更新任务状态，并可调用个人 RAG 知识库。
4. 企业级治理能力：用户角色分为 `user/admin`；普通问答和流式问答写入脱敏后的 `qa_logs`；管理员可分页查询用户、全局文档和问答日志；文档上传失败会回滚业务记录，删除文档会同步清理 MySQL 与 ChromaDB。

目前正式的 Agent 链路已经进入 `app/api/v1/agent.py`、`app/services/agent_service.py`、`app/schemas/agent_schema.py` 和 `app/utils/agent_context.py`；Agent HTTP 接口已经接入 `get_current_user`，会话历史与删除会校验归属关系。管理员查询位于 `app/services/admin_service.py`，问答日志位于 `app/services/qa_log_service.py`。正式回归测试位于 `tests/`，历史原型与调试脚本已移出项目，避免与产品代码继续混放。

## 二、技术栈

| 类别 | 技术 |
| --- | --- |
| Web 框架 | FastAPI + Uvicorn |
| ORM / 数据库 | SQLAlchemy + PyMySQL + MySQL |
| 数据校验 | Pydantic v2 |
| 认证 | JWT（python-jose）+ bcrypt（passlib） |
| 权限模型 | RBAC v1：`user` / `admin`，接口层通过 `require_admin` 校验管理员权限 |
| 向量库 | ChromaDB（磁盘持久化） |
| Embedding | BGE 中文向量模型（硅基流动接口） |
| 大模型 | DeepSeek（普通对话、流式、Function Calling；模型、地址、超时和重试次数支持环境变量配置） |
| Agent | 服务化 HTTP 接口：Function Calling → ReAct 循环 → Redis 多轮记忆 → 会话管理 → 学习评价 / 进度预警 / 任务规划 / 统一管家；历史原型脚本已外部归档 |
| 缓存与会话 | Redis：RAG 问答结果缓存 30 分钟；Agent 会话上下文 TTL 默认 30 分钟 |
| 文档解析 | PyMuPDF（PDF）、python-docx（DOCX） |
| 前端 | 原生 HTML/CSS/JavaScript + SSE |

## 三、分层架构

后端采用常见的分层结构，请求从上到下依次经过：

```text
浏览器/客户端
    │ HTTP
    ▼
app/api（路由层：接收请求、参数校验、返回响应）
    │ 调用
    ▼
app/services（业务层：业务规则与数据处理）
    │ 调用
    ▼
app/models + app/db（ORM 模型与 MySQL 会话）
    │
    └── RAG 场景额外调用：
        app/utils/text_splitter（分块）
        app/utils/llm_client（向量化 + 大模型）
        app/utils/vector_store（ChromaDB）
        app/utils/redis_client（缓存）
```

认证依赖通过 `app/core/security.py` 或 `app/core/deps.py` 的 `get_current_user` 注入到受保护接口中。当前两处实现仍并存：管理员接口与用户接口主要使用 `security.py`，文档、RAG、目标、任务和 Agent 接口使用 `deps.py`；后续应收口为唯一实现。所有接口统一使用 `app/core/response.py` 的响应格式，并由 `app/core/exception.py` 的全局异常处理器兜底。

Agent 现在也走标准 HTTP 分层：`app/api/v1/agent.py` 接收请求，`app/services/agent_service.py` 负责 Agent 调度、工具执行和会话管理，`app/schemas/agent_schema.py` 定义输入输出，`app/utils/agent_context.py` 负责 Redis 上下文持久化。原先根目录用于验证“TOOLS + execute_tool + agent_run”的原型脚本已移至桌面归档目录，不再参与正式应用导入和测试收集。

## 五、核心业务流程

### 1. 文档上传入库

```text
上传 PDF/DOCX
    → document_parser 解析纯文本
    → documents 表 add + flush 获取文档 ID，但不提交
    → text_splitter 分块（500 字/块、重叠 100 字）
    → llm_client 批量生成 BGE 向量
    → vector_store 写入 ChromaDB documents 集合
    → 每个分块写入 document_id、user_id、chunk_index 等元数据
    → MySQL commit，完成双存储写入
```

如果向量化或 ChromaDB 入库失败，服务会回滚 MySQL 事务，并按 `document_id + user_id` 幂等清理已写入的分块，避免留下数据库孤岛记录。删除文档时先删除可重建的向量分块，再删除 MySQL 业务记录。

### 2. RAG 问答

```text
用户提问
    → llm_client 生成问题向量
    → vector_store 按 user_id 强制过滤，必要时追加 document_id 过滤
    → 检索 TopN 相关分块
    → prompt_templates 组装系统提示 + 参考文档 + 问题
    → llm_client 调用 DeepSeek 生成回答
    → 普通接口：一次性返回答案 + 引用来源，并写入 Redis 缓存 30 分钟
    → 流式接口：SSE 逐字输出，结束后推送引用来源与 [DONE]
    → 成功、失败和缓存命中均写入 qa_logs；日志写入失败不影响回答
```

RAG 检索已经具备用户隔离；`qa_log_service` 会对问题、回答摘要和错误信息做长度限制与基础脱敏后再写入日志。

### 3. Agent HTTP 调用、工具执行与多轮上下文

```text
POST /api/v1/agent/chat
    → get_current_user 校验 JWT，并从数据库加载当前用户
    → app/api/v1/agent.py 校验 AgentChatRequest
    → app/services/agent_service.py 生成或复用 session_id
    → 复用会话时校验 session_id 是否属于当前用户
    → AgentContextManager 从 Redis List 读取历史；新会话写入 system prompt
    → llm_client.chat_with_tools(messages, TOOLS)：DeepSeek 判断意图
    → 模型返回 tool_calls（当前支持 update_task_status / list_tasks）
    → _execute_tool() 按 user_id 读写 MySQL，防止更新他人任务
    → assistant 工具请求和 role=tool 结果写回 Redis
    → 最多循环 10 步，模型不调用工具时返回最终回答和 intent_type

会话管理
    GET    /api/v1/agent/sessions                 查询某个用户的会话列表
    GET    /api/v1/agent/sessions/{session_id}    获取指定会话完整历史
    DELETE /api/v1/agent/sessions/{session_id}    删除指定会话
```

正式服务目前整合了任务完成管理、进度分析和学习规划三类提示词能力，但真正会写数据库的工具只有“查询任务”和“更新任务状态”。目标拆解、每日计划等落库能力仍主要存在于已外部归档的原型脚本中。会话消息本身有 30 分钟 TTL，但会话元数据和用户会话索引尚未同步设置 TTL。

## 七、运行方式

1. 启动 MySQL（连接信息在 `app/db/database.py`，默认 `ai_agent_db`），执行 `alembic upgrade head`，确保 `users`、`goals`、`tasks`、`documents`、`qa_logs` 表结构最新。
2. 启动 Redis（默认 `127.0.0.1:6379`）：RAG 问答缓存和 Agent 多轮会话记忆都依赖它。
3. 复制 `.env.example` 为 `.env`，填写数据库、Redis、JWT、DeepSeek 和硅基流动配置。
4. 安装依赖后启动：`uvicorn app.main:app --reload`。
5. 访问 `http://localhost:8000/docs` 查看接口文档，`http://localhost:8000/static/index.html` 打开演示页面。
6. 如需复现历史 Agent 原型，需要到桌面归档目录运行；运行前确保 MySQL、Redis 已启动且 `.env` 已配置，脚本会真实读写 `user_id=1` 等测试用户的数据。

## 八、当前已知问题与建议

1. `uploads/` 目录当前没有承载上传接口的持久化职责，上传接口只解析文件内容，不落盘保存原文件。
2. 根目录历史原型脚本已外移，后续应保持原型代码在外部归档目录演进，不再导入或复制回正式项目。
3. `AgentService._detect_intent()` 通过最终回复中的固定短语判断意图，提示词措辞变化后可能返回 `unknown`。

## 十、给新手的快速掌握计划（从大到小）

### 一句话理解整个项目

这个项目是一个“AI 学习助手”后端：用户注册后管理自己的学习目标和任务，上传 PDF/DOCX 形成个人知识库；DeepSeek 既能基于知识库做 RAG 文档问答，也能通过 Agent HTTP 接口和 Function Calling 调用真实业务工具，并借助 Redis 记住多轮对话，完成学习评价、进度预警、任务规划和会话管理。

### 第 1 层：看整体（1 小时）

目标：知道项目是做什么的、有几大块。

| 字段 | 处理规则 |

| `answer_summary` | 只保存回答摘要，不保存完整回答 |
| `latency_ms` | 覆盖检索、模型调用和流式输出总耗时 |
| `hit_knowledge` | 检索命中为 `true`，未命中或缓存命中按实际语义记录 |
| `status` | `success` 或 `failed` |
| `error_msg` | 失败时记录稳定错误类型，避免泄露密钥和底层堆栈 |
| `create_time` | 数据库统一生成或由服务层生成 |

执行约束：

1. 普通问答和流式问答都要记录，且缓存命中也要计入日志。
2. 日志写入使用独立数据库会话或后台任务，写入失败只记录应用日志，不影响正常回答。
3. 流式日志在生成结束后写入；中途异常写入 `failed`，但不得重复发送回答结束事件。
4. 管理员查询支持 `user_id`、起止时间、关键词和分页，默认按时间倒序。
5. 日志服务对外暴露清晰的函数，例如创建日志、分页查询和摘要脱敏；路由不感知数据库细节。

### 5. 9月18日：管理员接口与数据一致性

管理员接口计划使用以下边界：

| 方法 | 路径 | 服务职责 | 鉴权 |
| --- | --- | --- | --- |
| GET | `/api/v1/admin/users` | 分页查询用户，邮箱脱敏，不返回密码 | admin |
| GET | `/api/v1/admin/documents` | 查询全局文档元数据，不返回全文 | admin |
| GET | `/api/v1/admin/qa-logs` | 按用户、时间、关键词分页查询日志 | admin |

`admin_service.py` 负责数据范围、排序、分页和字段脱敏。`require_admin` 继续放在接口依赖层；普通用户返回 403，未登录返回 401。

删除文档采用“先删可重建索引，再删业务事实”的顺序：

```text
校验文档归属
    -> 查询或构造 document_id + user_id 过滤条件
    -> 删除 ChromaDB 中对应分块
    -> 删除 MySQL documents 记录
    -> 返回删除结果
```

如果向量删除成功、MySQL 删除失败，文档元数据仍保留，可再次执行删除并保持幂等；如果向量删除失败，不删除 MySQL 记录，避免出现用户无法再次定位和清理的孤儿向量。上传链路则需要补齐失败清理或对账策略，避免 MySQL 有记录而向量库无分块。
